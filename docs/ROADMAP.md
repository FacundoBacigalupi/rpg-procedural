**Fuente única de "qué sigue".** Cuando preguntes "¿con qué seguimos?", la respuesta sale de la sección **Ahora** de este archivo. Al terminar algo: marcarlo, moverlo y elegir el siguiente.

Construcción por capas: cada fase deja algo **jugable o inspeccionable**.

Estado: `[ ]` pendiente · `[~]` en curso · `[x]` hecho

### Cómo se trabaja (una sesión = un ítem)
El usuario abre **una sesión nueva por ítem** para no gastar contexto, así que cada ítem tiene que entrar en una sesión y terminar sin ambigüedad.

1. **Estados:** `[ ]` pendiente (no se empezó) · `[~]` en curso (solo durante la sesión; con sub-ítems) · `[x]` hecho. Un ítem no se deja `[~]` al cerrar la sesión: o está `[x]` o se parte (punto 3).
2. **Elegir:** el siguiente es el **primer `[ ]` de la fase actual** (la primera fase con `[ ]`), sin saltear. Si es demasiado grande para una sesión, **antes de codear** se parte en sub-ítems `[ ]` (cada uno entra en una sesión, con el doc de sistema y la sección que cita) y se hace solo el primero. El partido va al ROADMAP en el mismo PR.
3. **Cerrar:** el ítem hecho queda `[x]` con una frase de lo que hizo y las decisiones. **Todo lo que no se hizo** se escribe como ítem `[ ]` propio, con nombre, en la fase que corresponde (si depende de un sistema posterior, en la fase de ese sistema, prefijado `Heredado de <ítem>:`). Nunca se escribe «queda X» ni «falta Y» dentro de un `[x]` sin que X o Y sean un `[ ]` en otro lugar.
4. **Dejar «Ahora» apuntando** al ítem siguiente por nombre, para que la sesión nueva lo tome sin preguntar.
5. **Si una fase se queda sin `[ ]` que se puedan hacer**, se revisa que todo lo planeado esté hecho, se pasa a la fase siguiente lo que dependa de ella, se hace el PR `develop` → `main` y el tag.

### Receta por ítem de código
1. `git switch develop && git pull`, después rama `feat/<nombre>`.
2. Leer el doc de sistema que el ítem cita y [ARCHITECTURE.md](ARCHITECTURE.md) (§4 tipos, §7 herramientas). Si el doc no alcanza, se completa en el mismo PR.
3. Tests primero cuando se pueda; uno de determinismo si toca la sim; fast-check para conservación y propiedades. `npm run check` (typecheck + lint + tests) tiene que pasar.
4. En el mismo PR: cerrar el ítem como en el punto 3 de arriba, actualizar el doc del sistema si la implementación decidió algo, los comandos de CLAUDE.md si cambian, y «Ahora».
5. Commit (`feat(<scope>): ...`), push, `gh pr create --base develop --label feature`, y mergear con `gh pr merge <n> --squash --delete-branch` **como comando suelto** (una línea, sin encadenar). Sin CI en develop: la verificación es local.
6. Al cerrar una fase o un hito: PR `develop` → `main` con `gh pr merge <n> --merge --auto` y tag `v0.<fase>.<n>` sobre el merge commit ([GIT_WORKFLOW.md](GIT_WORKFLOW.md)).

## Fase 0 — Fundamentos (hecha 2026-10-06, `v0.0.1`)
